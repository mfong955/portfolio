Airbyte Issue Analyst

A 2-day interview project for a Senior Developer Advocate role at Airbyte—an end-to-end AI pipeline that ingests GitHub issues using PyAirbyte, enriches each one with Claude-powered structured analysis, and surfaces developer advocacy opportunities through a natural language Q&A agent.

Built with: Python, PyAirbyte, DuckDB, Claude, Streamlit
Context: Late-round interview assignment — Airbyte Senior Developer Advocate
Timeline: 2 days

The Problem

The airbytehq/airbyte GitHub repository has thousands of open issues. No one person can read them all, but developer advocates need to know: where are developers confused? What features are being requested? Where is the documentation failing them? This pipeline automates that triage.

What I Built

The tool has three layers, each demonstrating a distinct capability:

  • Data ingestion (PyAirbyte): Uses the production source-github connector—no mocks—to sync live issues from the Airbyte repository into a local DuckDB database, filtered to advocacy-relevant labels (documentation, question, enhancement, good first issue).
  • AI enrichment (Claude): Calls Claude once per issue to extract structured signal: pain point category, sentiment, whether it represents an advocate opportunity, and a specific recommended action. Idempotent—safe to re-run.
  • Natural language Q&A agent (Claude + Streamlit): A two-call agent that translates plain English questions into SQL, runs them against the enriched database, and returns a plain-language interpretation alongside the generated query and raw results.

What You Can Ask It

The Streamlit UI ships with pre-loaded demo questions that illustrate the kind of developer advocacy intelligence the pipeline surfaces:

  • What documentation gaps come up most often?
  • Which issues represent the best developer advocate opportunities?
  • What features are developers requesting most?
  • Give me 3 specific advocate actions based on these issues
  • What connectors or integrations are mentioned most?

Each answer shows the generated SQL, a plain-language interpretation, and the raw results table—making the reasoning transparent and auditable.

What This Demonstrates

  • PyAirbyte as real infrastructure: The actual production connector ingests live data—not a JSON fixture or a mock.
  • Claude for both batch and conversational tasks: Structured JSON extraction at scale for enrichment; few-shot text-to-SQL for interactive Q&A.
  • Genuine utility: Community pain points are mapped to concrete developer advocacy actions, not just categorized.
